# Godot 代码规范

## 优先级

1. 项目明确规则；
2. 项目现有且一致的代码风格；
3. 本文默认建议；
4. Godot 官方风格指南。

不要为了套用通用规范，批量重写与当前目标无关的旧代码。

## GDScript 默认规范

- 文件名、目录、函数和变量使用 `snake_case`。
- 类名和场景节点名使用 `PascalCase`。
- 常量使用 `UPPER_SNAKE_CASE`。
- 私有成员使用 `_` 前缀。
- 信号使用能描述已发生事件的名称，例如 `health_changed`、`item_equipped`。
- 新建长期维护代码写清函数参数和返回类型；重要状态、集合和公共边界写清变量类型。
- 项目要求完全静态类型或禁止 `:=` 时严格服从；项目允许渐进类型时，不因规范升级迁移无关代码。
- 一个函数只承担一个清晰目的；注释解释原因、约束和陷阱，不逐句翻译代码。

## 版本安全

- 先确认 `project.godot` 和项目文档中的精确 Godot 版本。
- 不确定类、方法、属性、信号、枚举或生命周期时，查看同版本官方文档或源码。
- 不凭记忆混用 Godot 3 与 Godot 4 的名称和调用方式。
- 第三方示例先确认版本再复制；能解析不等于行为正确。

## 结构选择

- 已知所有者调用其子对象时，优先清晰的直接调用；跨所有权边界的事件再使用信号。
- 只有真正跨场景、贯穿应用生命周期且唯一的服务才考虑 Autoload（自动加载）；不要把普通工具类和局部状态都做成全局单例。
- Resource（资源）适合可编辑、可复用和可保存的数据；Node（节点）适合生命周期、场景关系和表现。按实际用途选择，不机械套用。
- 优先组合小职责对象；只有确实共享稳定行为时使用继承。
- 抽象应来自至少一个已经跑通的真实案例。没有第二种需求前，不预建万能规则层、万能面板或万能配置系统。

## 用户界面

- 先设计用户最短路径，再设计场景树。
- 使用 Container（容器）、锚点和主题处理布局，避免用大量绝对坐标拼界面。
- 地图或游戏世界上方的界面必须正确消费其区域内的输入；全局世界交互应让界面先处理事件。
- 不用一个技术模块对应一个面板。相关信息尽量在用户作决定的地方呈现。
- 为高频动作减少点击，为危险动作提供清楚的结果和恢复方式，而不是一律叠加确认弹窗。

## 改动边界

- 完成用户当前目标所需的最小修改。
- 不顺便改名、格式化整个目录、迁移类型风格或重构邻近系统。
- 公共接口、存档格式和资源结构发生变化时，明确兼容性和迁移方式。
- 测试数据使用隔离目录或临时数据，不接触正式存档和用户资源。
