# Godot 代码规范

## 优先级

1. 项目明确规则；
2. 项目现有且一致的代码风格；
3. 本文默认建议；
4. Godot 官方风格指南。

不要为了套用通用规范，批量重写与当前目标无关的旧代码。

## GDScript 默认规范

- 文件名、目录、函数和变量使用 `snake_case`。
- 类名和场景节点名使用 `PascalCase`。
- 常量使用 `UPPER_SNAKE_CASE`。
- 私有成员使用 `_` 前缀。
- 信号使用能描述已发生事件的名称，例如 `health_changed`、`item_equipped`。
- 新建长期维护代码写清函数参数和返回类型；重要状态、集合和公共边界写清变量类型。
- 项目要求完全静态类型或禁止 `:=` 时严格服从；项目允许渐进类型时，不因规范升级迁移无关代码。
- 一个函数只承担一个清晰目的；注释解释原因、约束和陷阱，不逐句翻译代码。

## 版本安全

- 先确认 `project.godot` 和项目文档中的精确 Godot 版本。
- 项目使用 Godot 4.7 时，不确定类、方法、属性、信号、枚举或生命周期，先搜索 `godot-ai-devkit/references/godot-4.7-docs/`；不要一次加载整套文档。
- 项目不是 4.7 时，使用匹配版本官方文档；随包 4.7 文档可以帮助发现关键词，但不能证明其他版本行为。
- 公开文档没有说明且实现依赖内部顺序时，再查看同版本引擎源码完整调用链。
- 不凭记忆混用 Godot 3 与 Godot 4 的名称和调用方式。
- 第三方示例先确认版本再复制；能解析不等于行为正确。

## 结构选择

- 已知所有者调用其子对象时，优先清晰的直接调用；跨所有权边界的事件再使用信号。
- 只有真正跨场景、贯穿应用生命周期且唯一的服务才考虑 Autoload（自动加载）；不要把普通工具类和局部状态都做成全局单例。
- Resource（资源）适合可编辑、可复用和可保存的数据；Node（节点）适合生命周期、场景关系和表现。按实际用途选择，不机械套用。
- 优先组合小职责对象；只有确实共享稳定行为时使用继承。
- 抽象应来自至少一个已经跑通的真实案例。没有第二种需求前，不预建万能规则层、万能面板或万能配置系统。

## 用户界面

- 先设计用户最短路径，再设计场景树。
- 使用 Container（容器）、锚点和主题处理布局，避免用大量绝对坐标拼界面。
- 地图或游戏世界上方的界面必须正确消费其区域内的输入；全局世界交互应让界面先处理事件。
- 不用一个技术模块对应一个面板。相关信息尽量在用户作决定的地方呈现。
- 为高频动作减少点击，为危险动作提供清楚的结果和恢复方式，而不是一律叠加确认弹窗。

## UI 场景组件与脚本职责

正式、稳定且具有独立职责的 UI，优先用 `.tscn` 表达节点层级、容器布局、锚点、主题和初始可见状态。脚本负责数据绑定、状态转换、信号处理和调用领域逻辑；不要让一个控制器脚本同时成为界面树生成器、布局文件和业务控制器。拆分必须同时考虑可视编辑、复用、测试和降低耦合的收益，以及新增文件、节点路径和信号连接的成本。

以下是拆分信号，不是机械计数规则。满足多项，或其中一项已经足以形成独立职责时，应建立独立 `.tscn` 组件，而不是继续在 `_ready()` 或 `_build_*_ui()` 中堆 `.new()`／`add_child()`：

- 面板有自己的标题、容器层级、主题、尺寸或显示／隐藏生命周期；
- 包含多个交互控件或一个完整用户任务，可以独立预览、实例化或测试；
- 会被多个父界面复用，或同一种结构会按数据重复出现；
- 节点数量和职责已经让脚本难以一眼看清，继续增加功能会同时修改布局、引用、信号和业务状态。

推荐结构：

- 根屏幕或 HUD（抬头显示）场景只负责组合区域；顶部栏、底部栏、侧栏、表单、结果卡和弹窗等稳定区域按职责实例化子场景。
- 数据驱动的可变列表可以在代码中决定数量，但每一行、卡片或槽位优先实例化一个 `PackedScene`（打包场景）模板；不要为每条数据重新手写整组 Label／Button／Container（文本、按钮、容器）创建代码。
- 父组件向子组件传入数据或调用窄方法；子组件用信号报告用户动作。父脚本不应依赖子组件内部深层节点路径。
- 小型、一次性、真正临时的视觉反馈，或节点数量由运行时算法决定且没有稳定编辑器布局的内容，可以代码生成。动态不是默认理由，必须说明为什么 `.tscn` 不适合。

不要走向另一个极端：两个紧密耦合、只使用一次的简单节点不必各自拆文件。判断标准是能否独立理解、编辑、预览、复用和测试，而不是机械计算文件数。

修改既有脚本生成 UI 时，若本次改动会继续扩大节点层级、交互状态、重复模板或脚本职责，应先把受影响区域提取为 `.tscn`，再添加功能；不要以“以后统一重构”为由继续扩大单脚本界面树。纯局部缺陷修复且结构没有继续增长时，优先最小修复，不强制借机重构整个面板。

## 改动边界

- 完成用户当前目标所需的最小修改。
- 不顺便改名、格式化整个目录、迁移类型风格或重构邻近系统。
- 公共接口、存档格式和资源结构发生变化时，明确兼容性和迁移方式。
- 测试数据使用隔离目录或临时数据，不接触正式存档和用户资源。
- 大型脚本和文档使用正常文件补丁或本地文件工具修改；经远程文本接口大段覆盖后，检查文件末尾、关键函数和 NUL（空字符）。
