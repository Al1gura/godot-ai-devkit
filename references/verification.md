# 验证矩阵

| 改动类型 | 自动测试 | 运行态检查 | 原生可见窗口 | 用户产品验收 |
|---|---:|---:|---:|---:|
| 文档、命名、静态配置 | 有格式风险时 | 否 | 否 | 否 |
| 纯数据和算法 | 是 | 涉及 Godot 序列化时 | 影响渲染时 | 通常否 |
| GDScript/C# 逻辑 | 是 | 涉及节点、信号或实时状态时 | 依赖窗口、渲染或真实输入时 | 通常否 |
| 场景树、信号、生命周期 | 是 | 是 | 可见行为改变时 | 在稳定工作流验收 |
| 界面、拖放、滚动、焦点、快捷键 | 是，使用真实视口坐标 | 是 | 涉及真实输入或窗口行为时必须 | 高频、多步骤或难恢复时 |
| 2D/3D 渲染、着色器、相机 | 能自动化的逻辑 | 是 | 是 | 涉及可读性、手感或投屏时 |
| 多窗口、多显示器、分辨率、缩放 | 能自动化的逻辑 | 是 | 是 | 真实设备环境影响体验时 |
| 音频、视频和平台接口 | 是 | 是 | 是 | 主观质量或真实设备相关时 |
| 内部重构且外部行为不变 | 现有回归 | 生命周期风险改变时 | 否 | 否 |

## 四类证据分别证明什么

- 自动测试证明同样输入能稳定得到正确结果。
- 运行态检查证明当前 Godot 实例中的节点、信号、状态和时序符合预期。
- 原生可见窗口证明真实图形、输入、窗口和操作系统行为。
- 用户产品验收证明目标用户能找到入口、理解流程并愿意使用。

一种证据不能冒充另一种。自动测试全绿不代表流程好用；用户觉得顺手也不能证明数据和规则没有回归。

## 界面输入

覆盖在地图或游戏世界上的界面，应通过 Viewport（视口）发送带真实坐标的事件，既断言界面发生预期变化，也断言世界没有误触。直接调用 `_input()` 或 `_gui_input()` 只能证明局部函数，不证明真实分发顺序。

滚动测试覆盖正常位置、顶部和底部边界；拖放和焦点测试覆盖界面内、界面边缘和世界空白区。

## UI 场景组件

- 新增或大改正式界面时检查场景结构：稳定面板、表单、结果卡、侧栏和可复用区域应能作为 `.tscn` 独立实例化；父场景只组合组件并连接公开信号，不在脚本里重建子组件内部节点树。
- 数据驱动列表检查“静态容器场景＋重复项场景模板＋运行时实例化”的边界。测试可以改变条目数量，但不应要求控制器逐个创建每个条目的内部 Label／Button／Container。
- 每个独立 UI 组件至少验证一次单独实例化、必要节点与公开信号／方法，再通过正式父场景验证组合关系；只测试巨型主场景会掩盖组件所有权和深层节点路径问题。

## 用户产品验收时点

不要把每个中间类、临时面板或脚手架交给用户反复测试。等入口、上下文和退出方式稳定后，用一个真实目标场景验证最主要风险，并只询问最少反馈问题。

自动化能够验证的技术正确性由开发过程负责，不能让用户代替程序找普通缺陷。
