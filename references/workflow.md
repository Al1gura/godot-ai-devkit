# 通用开发流程

## 1. 定义真实结果

- 说明目标用户、使用情境、期望结果和最短路径。
- 明确当前请求的边界以及不做的内容。
- 如果现有设计已经让简单目标变复杂，先减少步骤和界面，再讨论增加功能。

## 2. 建立当前事实

- 读取项目规则、产品文档、相关代码/场景/资源、测试和当前 Git 状态。
- 对比文档与实际实现；有矛盾就公开指出。
- 缺陷先复现或取得真实坏状态，再决定修改位置。

## 3. 搜索可复用方案

- 先找项目现有模式，再找 Godot 官方能力和维护中的开源方案。
- 只对新增不确定性调查；已经验证且条件未变的结论直接复用。
- 记录采用、不采用和自行实现的理由，避免后来者重复调查。

## 4. 实现最小端到端改动

- 先让一个可信用户案例从入口到结果完整跑通。
- 只增加该案例实际需要的数据、状态、界面和抽象。
- 保持项目现有风格，保护无关改动和用户数据。
- 遇到会改变产品方向、破坏数据或需要新权限的分叉才暂停询问。

## 5. 按风险验证

1. 静态检查：解析、格式、链接、配置和差异检查。
2. 专项自动测试：证明确定性逻辑和修复目标。
3. 相邻回归：只覆盖共享同一合同的邻近行为。
4. 运行态检查：涉及节点、信号、生命周期、输入或实时状态时使用。
5. 原生可见窗口：涉及真实渲染、操作系统输入/窗口、多显示器、音视频、分辨率缩放或图形处理器时使用。
6. 用户产品验收：在稳定端到端成果上验证可发现性、文案、操作负担、恢复和主观体验。

## 6. 记录可交接状态

不要问“这是大阶段还是小阶段”，改问：

> 如果现在换一个不了解本次对话的人接手，仓库现有记录是否足以让他知道结果、决定、证据和剩余风险？

答案为否且状态已经具有持续价值时，更新唯一日志/状态入口。一次连续修改只在形成新事实时记录，不按内部步骤重复追加。

## 7. 报告

先说用户获得的结果，再报告改动位置、未做内容、直接相关的验证和剩余风险。程序验证与用户产品验收分开表述。
