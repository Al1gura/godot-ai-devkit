# 现成方案优先

## 触发方式

触发点是“实现需要作技术选择”，不是用户有没有说“查插件”“照 Godot 做”或“不要重复造轮子”。新增交互、编辑器行为、资源流程、外部格式、平台能力、复杂算法或依赖时，AI 应主动寻找成熟方案。

纯文案、简单改名、删除多余范围、已验证模式内的小改动不需要重新做广泛调查。

## 搜索顺序

1. **项目内部**：寻找已经使用并验证过的代码、场景、测试和决定。
2. **Godot 官方**：核对目标精确版本的公开接口、文档、演示项目、内置节点和官方插件。
3. **开源生态**：搜索 Asset Library（资源库）、GitHub 和英文社区中的维护方案。
4. **引擎源码**：行为依赖未公开顺序、导入/缓存、编辑器内部交互或文档与实测冲突时，查看目标版本源码完整链路。
5. **自行实现**：前面方案无法满足真实需求时，编写覆盖当前成功案例的最小实现。

## 不是“有插件就装”

采用现成方案前检查：

- 是否支持项目精确 Godot 版本；
- 最近是否仍维护，未解决问题是否影响当前用途；
- 许可证能否用于项目及再发布；
- 是否支持目标平台和导出方式；
- 是否引入超出需要的依赖、界面或数据模型；
- 是否与已有插件、输入、资源格式和架构冲突；
- 移除或替换成本是否可控。

一个庞大、停更或强迫项目改变工作流的插件，可能比几十行清晰的本地代码更差。复用原则的目标是减少风险和重复劳动，不是最大化依赖数量。

## 调研回执

需要新方案或外部依赖时，在实现前简短公开：

- 真实问题和项目现状；
- 找到的候选方案及版本/维护状态；
- 采用哪一部分；
- 不采用其他方案的直接原因；
- 自行实现的部分为什么无法复用。

已有同版本、同行为链的有效调研可以直接引用，只补本次差异。
