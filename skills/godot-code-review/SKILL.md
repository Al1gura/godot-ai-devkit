# Godot Code Review

## 审查边界

- 用户只要求审查时，读取和报告问题，不自动修改、提交或推送。
- 先理解产品目标、目标 Godot 版本、项目规范、改动差异和已有测试。
- 只评论本次范围内或由本次改动暴露的具体风险；不要把个人风格偏好包装成缺陷。
- 结论必须指向文件、位置、触发条件和影响，不能只说“架构不好”。

## 优先级

1. 崩溃、错误结果、数据损坏、安全和无法恢复；
2. Godot 精确版本/API 不兼容，场景树、资源、信号和生命周期错误；
3. 输入穿透、窗口/渲染差异、保存重开和平台问题；
4. 用户无法找到入口、简单任务被多余界面和步骤复杂化；
5. 缺失或错误的自动测试、运行态、可见窗口和产品验收证据；
6. 已有证据表明的性能问题；
7. 明显降低维护性的重复和耦合。

格式、命名和注释只有违反项目规则或会造成误解时才列为问题。

## Godot 检查

- 使用的类、方法、属性、信号和注解是否与项目精确版本一致；
- 是否混入 Godot 3 写法或只在其他版本存在的成员；
- 节点和资源所有权是否清楚，释放、重复进入和场景切换是否安全；
- 信号是否重复连接、遗漏断开、发送陈旧对象或隐藏控制流；
- `await`、线程和延迟调用后是否重新验证对象与请求新鲜度；
- Resource（资源）共享是否导致实例互相污染；
- Autoload（自动加载）、事件总线和全局缓存是否真的必要；
- 用户数据与可重建缓存是否分开，测试是否隔离正式数据；
- 界面是否正确消费输入，世界交互是否给界面优先权；
- 每帧路径是否有重复加载、无界遍历或大量临时分配，并且是否有分析器证据。

## 产品检查

- 实现是否解决用户要求的结果，而不只是完成内部模块；
- 每个新增面板、控件和确认是否对应真实决定；
- 高频路径是否被技术分层增加步骤；
- 失败、取消和恢复是否清楚；
- 测试是否直接调用内部提供器，从而漏掉正式入口和上下文衔接。

## 验证检查

- 确定性逻辑有可重复测试；
- 场景、信号和实时状态改变有运行态证据；
- 渲染、真实输入和窗口行为有原生可见证据；
- 高频流程和主观体验在稳定里程碑有产品验收计划；
- 失败、跳过和不可用证据没有被包装成通过。

## 输出

先按严重程度列出可操作问题，每项包含位置、触发方法、影响和最小修复方向。没有发现问题时明确说没有发现，并指出仍未覆盖的测试或环境风险；不要为显得有内容而制造建议。
