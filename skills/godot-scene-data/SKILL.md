# Godot Scene and Data

## 先确定所有权

对每份状态回答：

- 谁创建它？
- 谁可以修改它？
- 生命周期跟随哪个场景、会话或存档？
- 谁只读取或呈现它？
- 销毁、切换场景和重新载入时如何清理？

所有权说不清时，不先加全局管理器、事件总线或缓存。

## 选择承载方式

- Node（节点）：需要场景树关系、生命周期回调、处理、物理、可见表现或编辑器摆放。
- Resource（资源）：需要在编辑器中配置、复用、保存或被多个实例引用的数据定义。
- RefCounted（引用计数对象）或普通脚本对象：不需要场景树但有运行时行为和临时状态。
- Dictionary/Array（字典/数组）：边界简单且结构局部；合同稳定后应考虑明确类型，避免到处靠字符串键。

不要为了“架构整齐”给每个字段增加一层类，也不要把业务数据直接绑死在界面节点上。

## 组织场景树

- 一个场景围绕一个清晰所有者或可复用单位组织。
- 当子树需要独立复用、独立编辑、独立生命周期或独立测试时再拆场景。
- 只为视觉分组增加 Node 时确认它不会改变 Transform（变换）、处理或输入行为。
- 父对象向明确拥有的子对象直接调用；子对象通过信号报告已发生事件；跨远距离通信使用窄接口或明确服务。
- 避免深层 `../` 路径、到处 `get_tree()` 搜索和把所有节点都挂到 Autoload（自动加载）。

## 场景和资源实例

- 区分资源本体、共享引用、局部副本和运行时实例，避免一个实例修改导致所有使用者一起变化。
- 加载、实例化、加入场景树、保存和清理是不同阶段；只在对应阶段依赖可用状态。
- 外部资源、导入资源和用户数据分别管理，缓存可以重建，用户源文件不可当缓存删除。
- 不确定 PackedScene（打包场景）、资源缓存或导入行为时，查询目标版本官方文档；依赖内部顺序时再查同版本引擎源码。

## 保存与迁移

- 存档保存业务真值，不保存可以重算的临时界面状态和缓存。
- 为长期数据记录版本；读取旧数据时显式迁移、默认或拒绝，不静默曲解。
- 保存过程尽量先写临时文件并验证，再替换正式文件；失败时保留原数据。
- 自动测试使用隔离目录，不打开、覆盖或清理正式存档和素材库。

## 架构门槛

新接口、提供器、控制器或抽象层必须解决当前已存在的变化原因。只有一个实现且没有第二种真实需求时，优先保留清晰的具体代码；从跑通的端到端案例中提炼，而不是从想象中的未来扩展反推万能框架。

完成后验证场景切换、重复进入、释放、保存重开和错误路径；没有生命周期风险的纯数据修改不为形式启动运行态工具。
