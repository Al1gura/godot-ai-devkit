# Godot Debugging

## 不先猜

没有真实报错、日志、错误状态、截图或稳定复现步骤时，不先改代码，也不堆诊断输出。先记录：

- 用户做了什么；
- 预期结果；
- 实际结果；
- 第一次出现的位置；
- 是否稳定复现；
- 当前 Godot 版本、项目路径和运行实例。

## 诊断顺序

1. 重现最小坏状态，保存完整错误文本和调用栈。
2. 读取磁盘上的当前代码、场景、资源和相关测试。
3. 确认编辑器打开的是同一项目和版本。
4. 确认运行树、日志和截图属于刚启动的当前实例，不是旧运行残留。
5. 查询精确版本文档，核对可疑 API、属性、信号和生命周期。
6. 使用最小探针区分代码、数据、缓存、导入、运行通道、渲染、平台或产品流程。
7. 得到根因后先建立能稳定失败的回归测试，再修改。

## 常见误判

- 没有红色解析错误，不代表函数执行到末尾；非法属性或运行错误可能让后续逻辑不发生。
- 编辑器报错行号与磁盘代码不一致，可能是缓存或导入状态陈旧；不要立刻按错误行重写代码。
- 新 `class_name` 类型只在已打开编辑器中失败，可能是全局类缓存落后；先比较干净解析和实际运行。
- 端口响应、工具文件存在或编辑器进程存在，不代表连接的是正确项目和最新实例。
- 无窗口测试等待渲染帧可能永远不返回；将纯逻辑与原生可见渲染测试分开。
- Windows 图形程序可能从启动器脱离，启动器退出码不代表游戏进程完成；使用适合该平台的可等待入口。
- Tree（树形控件）在选择回调中同步重建可能被引擎拒绝；记录意图并在允许的阶段合并执行。
- 重启电脑只适合已确认的僵死进程/端口等环境故障，不是普通代码问题的兜底答案。

## 缓存和重载

- 先比较磁盘、导入结果和真实运行状态，再判断缓存是否陈旧。
- 优先使用重新扫描、重新导入和重新打开受影响资源等温和办法。
- 不把删除整个缓存、重载会断开诊断通道的插件或重启电脑作为第一步。
- 清理前确认缓存可以重建且目标不包含用户源文件、存档或未提交资源。

## 修复完成

- 原坏状态已经由自动测试从红变绿；
- 相邻共享合同没有回退；
- 需要运行态、原生窗口或产品验收的风险已经取得对应证据；
- 临时日志和诊断开关已清理；
- 记录根因而不只记录改了哪一行；
- 失败、超时和缺失证据如实保留，不把“没有结果”写成通过。
